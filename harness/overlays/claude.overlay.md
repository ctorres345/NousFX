## Claude Code
- A missing tool is not a stop: load it with `ToolSearch` and continue. Report a blocker only after the obvious fix failed, and name what you tried.
- Code search and "where is X" questions: use the `Explore` subagent (Haiku). Docs and API lookups: use `researcher` (Haiku). Noisy build/test output: `test-runner` (Haiku). Prefer these over the cavecrew/caveman-explore skills.
- Before a PR, run the `review-loop` skill yourself (Skill tool): `/simplify`, then the Opus `reviewer` for max 5 rounds, once per feature, not per edit. Never wait for the user to type `/review-loop`. Order: when the work is done, ask the user once whether to open the PR; on a yes, run the review loop, then `gh pr create`, without asking again. It replaces running `/simplify` and `/code-review` by hand and is also the one for unattended `/goal` runs. A PreToolUse hook (`review-gate.py`) blocks `gh pr create` until a review is recorded for the current code; if blocked, run the loop instead of working around the hook. Skip only with the user's explicit approval, via `--mark --skip "<reason>"`.
- Any request to review, critique, polish, or optimize UI/UX, visual design, responsiveness, or accessibility: invoke the `ui-review` skill first, in any project. It detects the platform (Android/Compose, Flutter, iOS, web) and runs the matching design skills; do not improvise a UI review from memory or skip skills it lists.
- Token hygiene (long contexts are the main cost): do not Read whole files over ~20K chars (use Grep, offset/limit, or `Explore`) and never Read old session transcripts under `~/.claude/projects` (use `scripts/usage-report.py` or grep). Do not re-read unchanged files or screenshots in a session. Redirect long build/test output to a file and read only the tail or failures.
- One task per session or thread. When a task is done (PR opened or merged, or a natural stopping point), the topic changes, or context is large, tell the user in one line and offer `/handoff` then `/clear` or a new thread. Use `/compact focus on <topic>` at milestones instead. For large features, plan in one session and implement in a fresh one.
- Handoff (every project, no exceptions): before any planning, exploring, or edits on the first task of a session, check whether `.claude/handoff.md` (or a root `HANDOFF.md`) exists in the project, and if so read it first, even when the user did not mention it and even if it seems unrelated. Then check it against `git status` and the current branch before trusting it. Do not wait to be asked; if it is missing, say nothing.
- Suggested skills in a handoff (every project): treat a handoff's "Suggested skills" section as part of the plan for the work it names. When you plan or start that work in a later session, invoke the model-invocable skills it lists at the step each one names, or say in one line why one does not apply. Name the user-only ones in the plan and let the user type them. Do not wait to be reminded.
- Writing the suggested skills (`/handoff`, every project): one skill per line, each tied to the step it applies to (for example "`tdd` for the URL parsing, before the UI"), naming the next work first. Leave out skills that always apply (`review-loop` before a PR) and do not list a skill twice.
- Writing a handoff (`/handoff`) overrides the skill's save location: if the project already has `.claude/handoff.md` (or a root `HANDOFF.md`), update that file in place, keeping its structure and replacing stale parts (state, next steps, open risks); do not create a second copy. If the project has neither and is a git repo, ask the user once per session (in unattended runs do not ask: use the temp folder): "Create `.claude/handoff.md` and add it to `.gitignore`? A note in the temp folder is not found by the next session." On a yes, create the file in the project root (the git top level, so the next session finds it) and, run from there, unless `git check-ignore -q .claude/handoff.md` already succeeds, add `.claude/handoff.md` to that folder's `.gitignore` (no duplicate line), leave that edit uncommitted and tell the user; then write the handoff there. On a no, or outside a git repo, write the note to the OS temp directory and do not ask again that session. Finish by printing the full path of the file written; for the temp folder add that a new session will not find it on its own. Still redact secrets and reference commits, PRs and tickets by link instead of duplicating them.
- Fable is a premium resource (limited weekly allowance). Two Fable agents exist, both read-only:
  - `architect`: architecture decisions (module boundaries, data models, migration strategy, major dependencies), optimization and performance reviews (speed, memory, battery), and design reviews. Give it a short brief (goal, constraints, options, what to measure).
  - `reviewer-deep`: second-opinion code review for large or risky changes (security/auth, data migrations, concurrency, public API changes), or when the default `reviewer` was inconclusive.
- Do not wait to be asked. When a task fits one of the Fable cases above, or you judge deeper reasoning would clearly pay off, say so in one short line (why, and what it would look at) and ask the user for approval. Run it only after a clear yes, then summarize the result for the user to decide. Never run Fable agents unprompted or in unattended `/goal` runs.
- Prototype fidelity (any project): when work is based on an approved prototype or design (artifact, Figma, mockup), the prototype is the spec. (1) Tickets: every ticket built from it must link the prototype AND name the artboard or screen, and carry an acceptance criterion "matches the prototype: colors, sizes, radii, spacing, icons, states (open/pressed/selected/empty/dark)", with the concrete values that matter written in the ticket, not only a link. When creating or refining such a ticket, add this if missing. (2) Implementing: open and read the prototype source (not only the ticket text) before writing UI code, and list its concrete values (tokens, colors per element, dimensions, radii) in the plan. If the app lacks a token the prototype uses, say so and name the ticket that adds it. (3) Review: `review-loop` must hand the reviewer the prototype and ask it to list visual deviations as findings; before opening the PR, compare the emulator screenshots against the prototype yourself. (4) PR: the description states what was checked against the prototype and what deliberately differs (and which ticket covers it).
