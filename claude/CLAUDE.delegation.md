# Delegation policy
- Code search and "where is X" questions: use the `Explore` subagent (Haiku). Docs and API lookups: use `researcher` (Haiku). Noisy build/test output: `test-runner` (Haiku). Prefer these over the cavecrew/caveman-explore skills.
- Keep edits in the main thread. Re-read any file yourself before editing it; do not rely on a Haiku summary alone.
- Every subagent call needs an objective, expected output format, and boundaries. Max ~3 parallel agents for simple tasks.
- Before a PR, run the `review-loop` skill yourself (Skill tool): `/simplify`, then the Opus `reviewer` for max 5 rounds, once per feature, not per edit. Never wait for the user to type `/review-loop`. Order: when the work is done, ask the user once whether to open the PR; on a yes, run the review loop, then `gh pr create`, without asking again. It replaces running `/simplify` and `/code-review` by hand and is also the one for unattended `/goal` runs. A PreToolUse hook (`review-gate.py`) blocks `gh pr create` until a review is recorded for the current code; if blocked, run the loop instead of working around the hook. Skip only with the user's explicit approval, via `--mark --skip "<reason>"`.
- Any request to review, critique, polish, or optimize UI/UX, visual design, responsiveness, or accessibility: invoke the `ui-review` skill first, in any project. It detects the platform (Android/Compose, Flutter, iOS, web) and runs the matching design skills; do not improvise a UI review from memory or skip skills it lists.
- Token hygiene (long contexts are the main cost): do not Read whole files over ~20K chars (use Grep, offset/limit, or `Explore`) and never Read old session transcripts under `~/.claude/projects` (use `scripts/usage-report.py` or grep). Do not re-read unchanged files or screenshots in a session. Redirect long build/test output to a file and read only the tail or failures.
- One task per session or thread. When a task is done (PR opened or merged, or a natural stopping point), the topic changes, or context is large, tell the user in one line and offer `/handoff` then `/clear` or a new thread. Use `/compact focus on <topic>` at milestones instead. For large features, plan in one session and implement in a fresh one. At session start, if `.claude/handoff.md` exists and relates to the task, read it first and check it against `git status` and the branch before trusting it.
- Fable is a premium resource (limited weekly allowance). Two Fable agents exist, both read-only:
  - `architect`: architecture decisions (module boundaries, data models, migration strategy, major dependencies), optimization and performance reviews (speed, memory, battery), and design reviews. Give it a short brief (goal, constraints, options, what to measure).
  - `reviewer-deep`: second-opinion code review for large or risky changes (security/auth, data migrations, concurrency, public API changes), or when the default `reviewer` was inconclusive.
- Do not wait to be asked. When a task fits one of the Fable cases above, or you judge deeper reasoning would clearly pay off, say so in one short line (why, and what it would look at) and ask the user for approval. Run it only after a clear yes, then summarize the result for the user to decide. Never run Fable agents unprompted or in unattended `/goal` runs.
- Jira tickets and branches (any project): the branch for a ticket is always `cesar/<TICKET-KEY>` (for example `cesar/MOB-23`), created from the default branch, never `claude/...` or a slug. Use the exact key returned by Jira; if no ticket exists yet, create it first. The `review-gate.py` hook also blocks `gh pr create` from any other branch name; if the user approves an exception, record it with `--allow-branch "<reason>"`. Do not rename existing branches unless asked.
- UI/UX tickets (feature or bugfix): when creating or refining the Jira ticket, add an acceptance criterion that the PR includes screenshots (before/after for changes, light and dark where theming applies, relevant device sizes). If the behavior is motion, a flow, or a bug that only shows over time, require a screen recording instead of or besides screenshots. Capture them yourself (simulator, emulator, or browser) rather than handing it to the user, and attach them in the PR description (fill the PR template's Screenshots / recording section).
