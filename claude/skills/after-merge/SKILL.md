---
name: after-merge
description: Use when a PR for your own ticket is merged (you merged it, the user says it is merged, or a check shows it MERGED, also a merge made in the GitHub UI). Deletes its branches, moves the Jira ticket to Done, renders the report, runs the retro once a wave is done, then runs /handoff.
---

Run this once a PR for your own ticket is confirmed merged. A merge made in the GitHub UI is only seen when you next look, so check first.

1. **Confirm the merge.** `gh pr view <n or branch> --json state,mergedAt,headRefName,headRefOid,baseRefName`. Stop unless `state` is `MERGED`, `baseRefName` is the default branch and `headRefName` is your `<prefix>/<KEY>` for the ticket in hand.
2. **Delete the branches.** Only the ones you made: `<prefix>/<KEY>` and `<prefix>/<KEY>-shots`. If `git status --porcelain` is not empty, skip this step, report it and go on to step 3. Otherwise switch to the default branch and pull. Check each branch and each side (local, remote) alone; skip only the one that fails, report it, and go on:
   - `<prefix>/<KEY>`: a side that is missing or already gone counts as deleted. Delete a side only when its tip equals `headRefOid` (local: `git rev-parse`, remote: `git ls-remote origin <branch>`); a different tip means a commit landed after the merge, so keep it. A squash merge makes `git branch -d` refuse, so use `-D`.
   - `<prefix>/<KEY>-shots`: no such branch means nothing to do. It never merges, so use `-D`, and delete a local one only when its remote is gone with nothing ahead of the default branch (`git log origin/<default>..<branch>` empty) or its tip equals `git ls-remote origin <branch>`.
   - Remote delete: `git push origin --delete <branch>`.
3. **Move the ticket to Done.** Use the tracker in `docs/agents/issue-tracker.md` (its "Tools per action" section names the tool and the Done transition id); without that file, use the Jira MCP with the branch's key, and if the tracker is unreadable, skip and say so. On Jira, prefer the claude.ai Atlassian connector: load each deferred tool you call (`transitionJiraIssue`, and `executeRead` for the fallback) with `ToolSearch` (`select:<full tool name>`) before its first call, pass the site's `cloudId`, call `transitionJiraIssue` with `transitionName: "Done"`, and if that is rejected, list the transitions (`executeRead`, `name: "listJiraIssueTransitions"`) and pass `transitionId: "<id>"`. Never pass `transition: {id}` to the connector; it rejects it. Only a session with just the plugin Atlassian server uses that shape, with the id from its `getTransitionsForJiraIssue`. A ticket with several PRs stays open until the last one merges: list open PRs with `gh pr list --state open --limit 200 --json title,headRefName` and keep it open if one has a head of `<prefix>/<KEY>` or a title whose key list contains `<KEY>` (`NFX-85, NFX-86: x` counts for both); name it in the report.
4. **Render the report.** Also unattended: `python3 -B <review-loop skill folder>/scripts/session_report.py render --name <KEY>` from the repo (Claude Code: `~/.claude/skills/review-loop`; `python` on Windows; it says so when no decisions were logged; if the script is missing, say so and go on).
5. **Run the retro.** Unattended, or if step 3 left this ticket open or could not read the tracker, skip it and say so. A status Jira cannot read counts as not Done. Else look for `~/Releases/<project>/waves/*/<KEY>.brief.md` or `<KEY>.md` (the wave coordinator writes them; if several date folders match, take the newest). Found: every ticket with a `<KEY>.brief.md` or `<KEY>.md` in that folder is in the wave, counting only names shaped like a key (`NFX-12`), so not `followups.md` or `retro*.md`; if any is not closed in Jira (Done, Won't Do or Cancelled), skip and name the tickets still open; else run the retro over the whole wave. Not found: a solo ticket is a wave of one, so run it over this session. The pinned skill is `<skills folder>/retro/SKILL.md` (Claude Code: `~/.claude/skills`; agy: `~/.agents/skills`); if it is missing, say so, skip the retro and go on to step 6. If its `retro.md` (wave folder, or the solo ticket's report folder) already exists, skip and say so (one with no retro in it is a dead claim: delete it to run again); else write that file first to claim the run. Then read the pinned skill as a file and follow it, with the extras in `references/retro.md`. Read-only: never edit it. Cesar says yes to each finding before it is filed. An approved finding becomes a ticket: the retro never edits a rule or skill, so no rule or skill is edited without approval.
6. **Run `/handoff`.** Its own prompts stay in charge; do not write the note yourself. Unattended, skip it and say so.

Do all six unasked. Report what each step did, or why it stopped.
